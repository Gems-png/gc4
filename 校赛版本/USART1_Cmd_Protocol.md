# USART1 指令协议(0x20 / 0x21)

> 本文档**只描述 `0x20` / `0x21` 这一对指令/状态帧**,供上位机对接使用。
> 整机 USART1 协议的其它包(关节状态、里程计、Tag 数据、时间同步等)见
> [`USART1_Protocol.md`](USART1_Protocol.md)。
>
> **底盘微调**(`0x21` 数据段 `0x30`~`0x33`,前/后/左/右各走 3 cm)单独一份,
> 见 [`USART1_Nudge_Protocol.md`](USART1_Nudge_Protocol.md) ——
> 它和本文档共用 `0x20` / `0x21` 这套帧,只是数据段多了一组取值。

---

## 一、帧结构

沿用整机协议,**结构不变**:

```
AA 55 | type(1B) | length(1B) | payload(length)      总长 = 4 + length
```

- **无 CRC、无帧尾**,全小端
- `length` 是唯一的帧边界依据 → 接收方**必须做 (type, length) 白名单校验**
- 帧头 `AA 55` 与 5A A5 调试协议不同,两套可共线共存

本对帧只有 **1 字节**数据,所以**帧长固定 5 字节**:

```
下对上(MCU → PC)    AA 55 20 01 CC
上对下(PC → MCU)    AA 55 21 01 CC
```

## 二、`0x21` 指令下发(上→下,1 字节)

| 偏移 | 长度 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 1 | `cmd` | uint8 | 指令字,编码见下 |

| 指令字 | 含义 | 下位机动作 |
|--------|------|-----------|
| `0x00` | **空指令 / 心跳填充** | 不动作。帧有效,照常刷新在线心跳 |
| `0x01` | **二维码识别完毕,继续行进** | 开始 / 继续运动 |
| `0x02` | **抓取一次** | 执行一次抓取 |
| `0x30` ~ `0x33` | **底盘微调:前 / 后 / 左 / 右** | 朝该方向走 **3 cm** 后自动停下 |

> `0x00` 是"什么都不做"的**安全指令**:上位机在运动中(已收到 `0x10` 时)
> 可以发它 —— 既不打扰下位机、又能维持链路心跳。
>
> `0x30`~`0x33` 是**动作**,和 `0x02` 一样一次只发一发。它们**只在
> `0x20` 状态 = `0x01` 时被接受**,而且微调期间下位机把上报切成 `0x10`、
> 走完自动切回 —— 所以**下一发必须等重新看到 `0x01`**,不能按定时器连发
> (见 §四)。步长是下位机侧固定值,上位机**不传距离**;完整的拒绝规则、
> 时序和排障表见 [`USART1_Nudge_Protocol.md`](USART1_Nudge_Protocol.md)。
>
> 真正**非法**的是上面两段之外的其它值(`0x03` ~ `0x2F`、`0x34` ~ `0xFF`),
> 下位机一律丢弃,并计入 `aa55_rx_drop`。
>
> 收到任一有效指令时,下位机同时刷新在线心跳(与 `0x04` / `0x05` 一致),
> 否则下位机在空闲时不会去驱动执行器,命令会看着像没生效。

## 三、`0x20` 指令状态(下→上,1 字节)

| 偏移 | 长度 | 字段 | 类型 | 说明 |
|------|------|------|------|------|
| 0 | 1 | `state` | uint8 | 当前状态,编码见下 |

| 状态字 | 含义 | 上报方式 |
|--------|------|---------|
| `0x00` | **等待二维码** | 周期上报(100 ms) |
| `0x01` | **等待抓取指令** | 周期上报(100 ms) |
| `0x10` | **运动中** | 周期上报(100 ms) |

> `0x01` 在下位机代码和微调协议里也叫**"等待颜色信息"**——同一个状态、
> 两种叫法,看到那个词就按本表的 `0x01` 理解。微调(`0x30`~`0x33`)也
> **只在这一个状态里被接受**,这是唯一的"门"。

---

## 四、发送策略

- **下位机**:三个状态**一律每 100 ms 周期上报**,包括运动中(`0x10`)。
  本协议无 CRC,周期重发就是防丢帧手段 —— 上位机漏掉一帧,100 ms 内就能补上。
- **上位机**:只有在收到 `0x00` / `0x01`(等待中)时才发对应指令;
  收到 `0x10`(运动中)**不要发指令打扰下位机**,如必须发就发 `0x00`(空指令)。
- **微调(`0x30`~`0x33`)的节拍由下位机给**:发出一发后,下位机把上报切成
  `0x10`、走完(约 0.3 s)自动切回 `0x01`。**看到 `0x01` = 上一发走完了**,
  这时才能发下一发。收到 `0x10` 时发出去的微调会被**静默丢弃**(不计错、
  不缓存),所以"发完 sleep 0.5 s 再发下一条"的开环写法会少走几厘米,
  而且没有任何报错 —— 必须跟着 `0x01` 走。

## 五、整体时序(实战流程)

```
上位机(PC)                              下位机(MCU)
  │                                        │
  │                                        ├─ (手动/指令触发)启动 → 按既有序列走一步
  │ <─ 0x20 state=0x10 ─────────────────── │ 运动中(100 ms 周期上报)
  │                                        │
  │                                        ├─ 第 1 个弯 → 停下
  │ <─ 0x20 state=0x00 ─────────────────── │ 等待二维码(100 ms 周期上报)
  │ ── 0x21 cmd=0x01 ────────────────────> │ 二维码识别完毕 → 继续行进
  │                                        │
  │ <─ 0x20 state=0x10 ─────────────────── │ 运动中,按既有序列继续前进
  │            …  车在走  …                 │  (上位机:不要发指令,可发 0x00)
  │                                        │
  │                                        ├─ 第 3 个停止处 → 停下
  │ <─ 0x20 state=0x01 ─────────────────── │ 等待抓取指令(100 ms 周期上报)
  │ ── 0x21 cmd=0x30 ────────────────────> │ (需要才发)微调:前进 3 cm
  │ <─ 0x20 state=0x10 ─────────────────── │ 微调在走(约 0.3 s)
  │ <─ 0x20 state=0x01 ─────────────────── │ 走完自动回到等待 → 这时才能发下一发
  │            …  要挪几发就重复几次  …      │  方向/发数由上位机按偏差决定
  │ ── 0x21 cmd=0x02 ────────────────────> │ 抓取一次(第 1 次)
  │ <─ 0x20 state=0x01 ─────────────────── │ 回到等待抓取指令
  │ ── 0x21 cmd=0x02 ────────────────────> │ 抓取一次(第 2 次)
  │ <─ 0x20 state=0x01 ─────────────────── │
  │ ── 0x21 cmd=0x02 ────────────────────> │ 抓取一次(第 3 次)
  │ <─ 0x20 state=0x10 ─────────────────── │ 抓完 → **回到原序列继续运动**
  │            …  车在走  …                 │  ④~⑧ 接着跑完
```

> 微调是可选的、而且排在抓取**之前**:先靠它把车挪到正对物料的位置,
> 再发 `0x02`。微调期间那两行 `0x10` 是正常现象,不是下位机掉了。

**流程要点**

| 阶段 | 下位机上报 | 上位机下发 | 说明 |
|------|-----------|-----------|------|
| 启动 | `0x10` 运动中 | — | **不自启**。手动(`ms_start_req`)或指令触发后才走 |
| **第 1 个弯** | `0x00` 等待二维码 | `0x01` | 识别完才继续 |
| 继续前进 | `0x10` 运动中 | (不要发,可发 `0x00`) | 按既有序列走 |
| **第 3 个停顿点** | `0x01` 等待抓取指令 | `0x30`~`0x33` / `0x02` | 要挪就先微调对准,再抓取,共 3 次 |
| 抓完 | `0x10` 运动中 | — | **回到原序列继续运动**(④~⑧) |

---

## 六、握手规则

- **上位机**:只在收到 `0x00` / `0x01` 后发对应指令;收到 `0x10`(运动中)
  **不要发指令打扰下位机**,必须发就发 `0x00`(空指令,不动作)。
- **下位机**:三个状态一律 100 ms 周期上报,运动中(`0x10`)也照发。

---

## 七、备注与实现说明

**已定项**

- **3 次抓取握手(方案 A)**:每次抓完回 `0x01`,上位机再发 `0x02`,共发 3 次。
- **微调步长 3 cm、由下位机固定**:上位机只发方向(`0x30`~`0x33`),没有地方传距离;
  想走 9 cm 就发三次,且**每发之间要等回到 `0x01`**(见 §四)。
- **运动序列不自启**:由人 / 指令决定何时开始(`MS_AUTO_START = 0`),
  启动后才按既有序列走。

**段表对应关系**

按现有段表(16 段 = 8 个动作 + 8 个停顿,**全是平移、没有转弯段**):

- **"第 1 个弯" = 第 1 个停顿点** —— ①后退105 之后
- **"第 3 个停顿点" = ③前进105 之后** —— 抓完就从那里继续跑 ④~⑧

> 若序列要加转弯段、或调整停顿点位置,上面两处对应关系要跟着改。

**⚠ 下位机实现上尚缺的能力**

"抓完回到原序列继续跑"需要**路线中途挂起 / 恢复**:跑到第 3 个停顿点挂起 →
执行抓取 ×3 → 从第 6 段续跑。现有动作序列只有"从头跑到尾"和"整条停掉"两种,
没有中间挂起 —— 实现时需补上。
